# 启动零售服务

在仓库根目录按 README 安装固定上游和实测依赖。服务读取中文区域包中的商品目录、模拟账户、政策和区域设置。它只使用原生工具支持的七类写操作。模拟身份核验沿用基准的注册邮箱查找，成功后发放随机会话令牌。这里使用的是基准中的合成客户数据。

```bash
set -a
. ./.env
set +a
export RETAILOPS_BRIDGE_URL=http://127.0.0.1:18863/v1/
.venv/bin/python -m uvicorn retailops.api:app --host 127.0.0.1 --port 8000 --no-access-log
```

通过 `http://127.0.0.1:8000/docs` 使用可交互的接口。首次可从固定区域包选择一个模拟账户，在仓库目录运行以下命令查看对应邮箱。

```bash
.venv/bin/python -c "from retailops.domain import Domain; print(next(iter(Domain().seed['users'].values()))['email'])"
```

| 步骤 | 接口 | 使用方式 |
| --- | --- | --- |
| 开会话 | POST /sessions | 传入 `email`，此后的请求头填 `Authorization: Bearer <token>` |
| 查进度 | GET /state | 返回已核验用户、待办、会话修订号、方案版本、确认版本及阶段 |
| 提需求 | POST /messages | 传入 `message`、当前 `revision`、自选 `request_id` 及 `mode`（A/B/C） |
| 手动改方案 | POST /plan | 传入当前 `revision` 和全部 `actions`，每项包含 `tool` 和 `args` |
| 确认 | POST /confirm | 用户看完整个方案后传 `version`；模型不能调用此接口 |
| 查能否执行 | POST /preflight | 传 `version`，返回允许与否、原因及建议的下一步 |
| 执行 | POST /execute | 传确认过的 `version` 和业务 `request_id`；响应丢失时可用同一请求重放回执 |
| 取消生成 | DELETE /messages/{request_id} | 仅当前会话可取消其正在排队或运行的模型请求 |
| 订阅进度 | GET /events | SSE 支持 `Last-Event-ID` 续读；`?follow=false` 只返回已记录事件 |
| 健康检查 | GET /health | 检查服务能读取 SQLite；模型可用性由真实请求验证 |

`revision` 用于发现并发编辑，`version` 标识对用户展示的整套业务方案。用户修改任一项后，旧确认失效。新增自然语言消息进入处理时也会暂停待执行方案，防止用户改口期间执行旧版。含糊的“确认”需要用户选择所指版本。人工提交缺少字段的草案保留为“待补充”；模型拟案校验失败时可拿到结构化反馈，修改参数或向用户追问。

工具先在独立数据副本上检查整套方案。执行时使用 SQLite 写事务读取最新账户，再次运行原生工具。工具产生的订单或余额变更与幂等回执同时提交。确认过的同一版本即使用不同请求编号重试，也只会产生一次效果。不同会话的对话和确认彼此隔离，同一模拟账户的已提交订单变化对其其他会话可见。此保证的范围是当前 SQLite 内的模拟业务，真实支付网关需要另行对接其幂等键和对账接口。

默认每个服务进程允许 3 个模型请求同时执行，另有 6 个等待位，总期限 120 秒。模型通信采用异步 HTTP，SQLite 和业务工具在线程中运行。应用显式取消或超时会结束本次 HTTP 等待；配套新版桥接会检测请求连接关闭并清理其独立模型进程。使用一个服务进程便于准确限制队列容量和定位待取消的请求。

## 用容器启动

先完成固定源码准备。构建上下文只包含服务、锁定的依赖清单、上游包及中文区域数据。在 Linux 上沿用现有回环模型桥的启动方式如下。默认健康检查访问 8000 端口。

```bash
docker build -t retailops-agent:service-v1 .
docker run -d --name retailops-service --network host --env-file .env \
  -e RETAILOPS_BRIDGE_URL=http://127.0.0.1:18863/v1/ \
  -v retailops-state:/data retailops-agent:service-v1 \
  python -m uvicorn retailops.api:app --host 127.0.0.1 --port 8000 --no-access-log
```

## 复现评测

下列命令依次检查原业务与服务、模型桥、容器重建、历史成功写入、真实上下文对照及政策引用。正式重复试次使用新目录。模型试次的原始响应、事件和账本留在被 Git 忽略的 `runs/`；报告只发布任务级指标和汇总。需要观察模型启动与生成耗时时使用本仓库更新后的桥接，沿用项目可用的模型网络配置。

```bash
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m unittest discover -s model_bridge -v
.venv/bin/python scripts/service_container_check.py
.venv/bin/python scripts/service_replay.py runs/full50/native/zh-retail/results.json --output reports/service-replay.json
.venv/bin/python scripts/service_trials.py --output runs/paired-new --repeats 3
.venv/bin/python scripts/service_checks.py --output runs/checks-new
.venv/bin/python scripts/service_holdout.py --output runs/holdout-new
.venv/bin/python scripts/service_summary.py runs/paired-new --checks runs/checks-new --output reports/service-results.json
```

A 使用完整历史，B 在相同历史上增加结构化业务状态，C 保留状态、最近三个用户轮及最多两个匹配编号的较早证据轮。C 会分页显示较长的商品款式列表，保留价格、库存、选项与商品标识，可按原始商品编号继续查询。早期证据关联使用编号匹配，只有自然语言描述的指代仍可能丢失。政策问答按章标题与正文匹配关键词，并把中文业务词映射到原文术语。模型可调用检索工具取得原文与章节出处。
