# 零售 Agent 服务验证

2026 年 11 月 10 日在项目服务器验证。业务使用固定 τ-bench v2.0.0 中文区域数据及原生零售工具；模型通过项目已有 Codex 登录桥接，成功试次核验实际模型为 `gpt-6.1-sol`、强度为 `medium`。官方 50 题的 39/50 是此前 A0 原生基线。本次没有重跑新版的官方 50 题。

## 执行检查与恢复

在 20 个不同模拟账户上分别构造四个违规场景和一个合法场景，逐项读取操作后订单，检查是否产生了实际副作用。

| 场景 | 尝试数 | 被拦截 | 订单发生变更 |
| --- | ---: | ---: | ---: |
| 完整参数，用户尚未确认 | 20 | 20 | 0 |
| 增加退货商品后使用旧版确认 | 20 | 20 | 0 |
| 访问其他用户订单 | 20 | 20 | 0 |
| 缺少退款方式 | 20 | 20 | 0 |
| 完整方案已由本人确认 | 20 | 0 | 20 |

测试集违规执行率 **0/80**，合法请求误拦截率 **0/20**。上述分母来自确定性执行层测试。错误返回包含失败类型、原因和下一步；库存不足或退款渠道无效时，模型可修订待办并重新请求确认。

33 项业务、评测与服务测试和 16 项桥接测试全部通过。覆盖多需求、版本陈旧、确认指代、缺参数、库存替代、错误后改案、重复提交、执行成功后丢失响应。并发测试对同一版礼品卡取消订单同时发出 8 个请求，7 个取得已有回执；订单只新增 1 条退款记录，余额只增加 1 次。故障注入让写入回执中途失败，订单随事务回滚，重试成功。容器测试实际构建镜像、启动服务、取消一单、删除并重建容器，再从同一数据卷读取原回执。

## 原成功任务与失败分类

原成功的 39 道官方任务中有 35 道实际成功写入，另 4 道没有成功写调用。按历史顺序回放 35 道中的 **60 次成功写调用**，新版工具返回与原始返回逐字段一致 **60/60**，误拦截 **0/60**。每次回放由测试程序确认相应版本，这项结果只度量写操作兼容性。

原失败的 11 道按原生评分组件分组：6 道只未通过数据库终态，4 道同时未通过数据库终态及自然语言断言，1 道只未通过自然语言断言。逐题分类与终止原因可复核。具体根因仍需结合原始对话和政策判断。服务另记录身份不符、缺少参数、业务规则拒绝、版本或幂等冲突、队列已满、超时、取消和模型协议错误等运行事件。

## 上下文与模型耗时

两道新编中文任务分别要求从查单继续办理单项退货，以及在下一轮追加退货商品。每题前置五轮固定商品查询，证据来自原生工具的完整返回。每种上下文策略对同一任务重复 3 次，每次使用独立账本。判定核对方案中的订单、商品明细、退款渠道与提交后的数据库终态。

| 最终对照 | 成功 / 计划 | 实际输入 Token 总数 | 实际输出 Token 总数 | 每次任务耗时中位数 |
| --- | ---: | ---: | ---: | ---: |
| A 完整历史 | 6/6 | 220,694 | 1,145 | 19.34 秒 |
| B 完整历史加状态 | 6/6 | 221,791 | 1,121 | 19.07 秒 |
| C 状态、近期历史及早期证据 | 6/6 | 162,788 | 1,124 | 19.08 秒 |

C 相对 A 减少 **57,906 个输入 Token（26.2%）**。B 相对 A 增加 1,097 个（0.5%）。18 次完整试次中均无遗漏目标商品，无错误订单或退款渠道。输入 Token 包括模型桥实际报告的输入，不能据此推算具体账单金额。任务模板仅两种，前置长历史为实验构造，此处衡量的是特定长会话负载。

最终对照共有 **54 次模型往返**。模型往返中位数 6.365 秒，其中桥接会话启动中位数 0.337 秒、生成阶段中位数 5.903 秒。服务侧业务工具执行中位数 0.434 毫秒。队列、启动、生成、解析、工具执行和账本写入分别记录，支持按会话、请求及模型步骤追踪。账本写入事件记录到 SQL 语句完成，未单独计量 SQLite 提交刷盘。三个方案的任务耗时相近。

### 运行故障与分母

共保留四轮，每轮计划 18 次。第一轮代理配置缺失，18 次均在模型生成前失败。第二轮接入项目代理后通过 18/18。第三轮复测命令误改模型程序路径，18 次均在模型生成前失败，同时该轮 5 次政策问答返回 502。修正程序路径并核对可执行文件后，第四轮通过 18/18。上表使用第四轮，完整四轮 72 条记录及其失败分母均在去敏汇总内。每个试次的详细轨迹和政策问答原文留存在服务器 `runs/`。

## 冻结后的新任务验收

完成开发对照后另编两道任务，运行前记录服务、模型桥、测试程序及案例清单的摘要，运行结束再次核验代码。两题都使用 C 模式，先让模型提出初版方案并由用户确认，再提交新的用户意图。双订单取消和改退至已有礼品卡各独立运行三次。**6/6** 均拦住旧版，按新版更新正确订单和退款渠道，重发请求均取得原回执。这里覆盖两种新业务场景，未对 A/B/C 或原生 Agent 做额外排名。[冻结验收结果](service-holdout.json)

## 政策检索

对退款账户、信用卡退款时限、跨品类换货、修改商品次数和礼品卡余额五个问题，正确政策章节进入前三位 **5/5**，模型回答引用预期章节 **5/5**。逐条对照原文后，五个问题的主要结论均与条款一致。检索使用固定政策的章节、关键词和中英文业务词映射，模型同时可见完整业务政策。本次没有做移除检索的消融对照。

## 简历可用表述

- 为零售 Agent 的 7 类写操作实现方案版本确认、归属校验与事务幂等；在 20 个模拟账户的 100 个执行用例中，80 个违规请求均未产生业务变更，20 个合法请求全部执行。8 路并发退款仅入账一次。
- 设计完整历史、历史加状态、状态加近期证据三种上下文策略；在 2 道中文零售长会话任务的 18 次真实模型对照中，三组均通过 6/6，裁剪策略相对完整历史减少 26.2% 输入 Token。
- 使用 FastAPI、SQLite、SSE 和 Docker 交付多会话零售服务；通过提交中断回滚、响应丢失重试和容器重建恢复测试，回放历史成功轨迹中的 60 次写调用，工具结果全部一致。

用于 Agent 工程岗位时可优先选前两条。已有正式基线可继续单列 39/50。后续若希望写“提高任务成功率”，需要对两版 Agent 使用相同用户模拟、评分器和任务预算，完成正式重复试次对照。
