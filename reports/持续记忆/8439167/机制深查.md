# 持续记忆机制深查：为何未见收益，是否接入 Anthropic 原版

核查日期：2026 年 11 月 19 日。正式运行冻结提交：84391676e08c5cb13f7769b445791c5a96be3e60。本次只读复核一百九十八个评分位置、九十九次整理、实际注入与选定失败轨迹，没有重跑正式成绩或修改原记忆。

## 结论先说清楚

本次确实持续更新并使用了记忆，但没有接入 Anthropic 原生 Memory tool、Managed Agents memory stores 或 Dreams API，也没有完整移植官方 dreaming 示例。实际是自建的短笔记提炼与词项检索系统，使用 gpt-6.1-sol 模型桥接。此前若将其简称为“Anthropic 原版记忆机制”，不准确；应称“参考 Anthropic 后台整理思路的简化实现”。

问题并非单纯“记忆没更新”。更直接的线索是：部分暂缓经历被总结成通用办理前提，检索又把不适用的提醒送到当前业务；客服提出额外疑问，模拟顾客随后要求先核实，于是停在没有可用工具解决的等待中。代码没有有效区分“轨迹里出现过的说法”和“经过规则及反例验证的方法”。

这条解释有代码、历史更新和具体对话顺序支持，但仍是机制诊断，不是对全部分差的因果估计。没有进行“固定同一对话前缀，仅删除某条经验”的模型对照，不能声称每道退化都已证明由记忆导致。

## 一、具体失败是怎样发生的

### 第三轮第50题：企业发票提醒进入个人发票业务

1. 顾客先查物流并办理加急，这部分成功。
2. 顾客接着要求开个人发票，还没有提出税号或E卡开票资格问题。
3. 该请求实际注入了“个人发票信息确认”和“企业发票条件核验”两类经验。
4. 客服主动提出E卡付款的开票条件和税号要求尚未核实，并转接。
5. 顾客下一轮才要求继续核实这两个问题；后续一直没有得到能解决它们的查询结果，发票没有生成草案。

同轮关闭组也遇到默认开票信息不明确，但提出使用已查到的姓名、电话作为候选，请顾客确认。顾客确认后生成草案、点击确认、收到开票成功回执，整题为一分。持续组为零分。

“企业发票条件核验”这条经验在第一轮第52题失败后新增，此后没有修订。它在第二、三轮分别注入六十、五十六次，跨业务适用性没有程序约束。注入次数是会话请求次数，不是题数。

冻结上游开票工具的参数为抬头、订单、电话和发票类型；实现中没有税号参数或E卡资格查询环节。这里说明的是本基准环境的工具合同，不能推出真实零售业务无需遵守相关开票规定。当前问题是把没有获得本环境规则支持的额外核实要求，加入了这笔个人发票的前提。

证据边界：两组开场这一题完全一致，后续话术并不逐字相同；第二轮第50题持续组仍成功。因此这条记忆不是必然导致失败的开关，当前只能确认错误适用和随后的阻塞顺序。

### 第二轮第49题：有明确换货意愿，却等待工具体系之外的证据

顾客选定了可换列表中的目标商品，并明确要求先生成草案确认。客服当轮注入了“换货筛选与结算”经验，随后表示库存、换货结算价和退补差额仍待核实，转接后未生成草案。顾客才改为等核实，并继续咨询原商品赠品。整题零分，查询和输出通过。

该经验最初由第一轮第8题的成功轨迹形成，之后经第19、33题的失败轨迹扩展了结算、优惠及额外核实要求；第二轮第49题失败后，又加入了更明确的缺证暂缓条件。它呈现出“失败后继续强化等待要求”的沿革，而不是已经验证恢复办理的方法。

冻结上游把换货描述为可换列表内的平替，查询返回订单状态和可换列表；执行工具并没有另行查询换货结算价或退补流程的能力。这不表示可以忽略顾客明确提出的费用条件，而是经验必须区分：当前规则确实要求的条件、顾客本次新加的条件，以及模型从历史中泛化出的额外条件。

此前报告指出“未读到同题前轮来源”，不能据此判定只是检索漏召回。进一步检查发现，它读到了其他题形成的换货经验，而且这条经验本身可能使办理停住。是否含同题来源不是判断记忆有效性的充分指标。

### 第三轮第5题：不能把所有失败都归为没有草案

这题已经生成退货与E卡退款的完整草案。顾客未确认金额，并明确要求先查已退流水。客服因此暂停整组；已有授权不能被扩大，不能为了得分直接退款。

执行预检会从账本和回执核算退款金额，但面向模型的解释和可查询证据没有充分支撑后续流水追问。客服称现有工具无法查询流水或转接进度，交互随后反复等待。应检查如何把真实账本核验结果作为可查询、可解释的证据提供出来，不能把缺失证据当作零。

另一个独立问题发生在这题第一轮请求：顾客问维修政策，实际却注入“E卡适用性核验”和“故障代码与原因判定”。离线复现题前快照和首条输入，命中编号与原日志完全一致。相关的保修、维修费用经验在库里，但没有进入最终注入内容。

## 二、代码中确定存在的机制差距

### 更新有了，可靠性校验仍然很弱

每题后用一次模型请求生成最多三项新增、修订或删除；输入是旧记忆、当前可见轨迹、官方四个零一分量。没有单独的整体整理阶段，没有对失败猜测运行开发反例，也没有把完整业务政策和工具能力清单作为固定输入；只有实际查询到的规则可能出现在工具历史中。

程序检查证据序号存在、格式符合、字段脱敏、长度合规；不检查证据是否真的支持结论。纯函数合成诊断中，证据说“未签收可以取消”，相反的“只有签收才能取消”规则仍被接受并标成“有轨迹支持”。这只用于证明校验边界，未写入正式库。

轮末条目数分别为三十、三十五、四十一，全部标成“有轨迹支持”，没有“待验证”条目。代码允许待验证，但这三轮没有实际形成区分。没有删除动作不单独证明错误，但结合未修订的企业发票提醒，说明不能把整理次数等同于有效纠错。

### 检索看相同词，缺少业务适用性判断

检索将顾客当前消息与未结事项的原话合并，计算中文二字词和英文词的交集；相同时优先最近修订，再按编号。没有个人/企业发票、咨询/办理、已满足/未满足条件的硬性筛选，也没有重新核验建议与当前规则是否冲突。

第5题首条请求的E卡、参数比较、维修路径、保修经验都只匹配两个词项，较新的E卡笔记排在前面。随后受八百字节总预算影响，其他较长笔记可能放不进去。实际九百七十六次非空注入中，七百九十次只有两条，占约百分之八十一；最多三条不等于每次获得三条最相关经验。

预算小本身不是错误，官方也强调保持注入精简；这里的问题是没有适用性筛选，却用长度和更新时间参与决定留下什么。也不能据此直接建议无限增大上下文。

### 经验只是一段提示，没让业务恢复变成稳定动作

检索在每个顾客请求开始时运行一次；后续八步内查询或更新事项后，不会重新检索。模型只看注入的短文本，没有读取更多记忆或回查旧证据的专用工具。代码依然依靠模型自己判断何时调用拟案工具，没有因为“记住应恢复办理”就保证生成草案。

三轮失败阶段如下。各行分类按事件互斥计数；“没有草案”不自动等于错误，可能是顾客暂缓或条件确实缺失。

| 轮次 | 条件 | 整题失败 | 无可确认草案 | 有草案但无确认 | 已办理部分事项但整题失败 |
|---|---|---:|---:|---:|---:|
| 一 | 关闭 | 16 | 8 | 0 | 8 |
| 一 | 持续 | 20 | 16 | 0 | 4 |
| 二 | 关闭 | 19 | 11 | 0 | 8 |
| 二 | 持续 | 24 | 14 | 0 | 10 |
| 三 | 关闭 | 18 | 10 | 1 | 7 |
| 三 | 持续 | 25 | 13 | 1 | 11 |

持续组三轮指定查询分别通过三十二、三十一、三十三题，输出均通过三十三题，终态只通过十三、九、八题。主要损失在完成业务，而不是整批查询或格式失败。关闭组平均每题约九点七轮，持续组约十一点六轮；这是对话轮数描述，包含合理追问和重复等待，不能仅凭平均数确定原因。

## 三、与 Anthropic 官方机制逐项比较

Anthropic 有多种相关产品和实现，不能合称一个保证增益的“原版算法”。

| 对照项 | 官方公开能力或示例 | 本次实际运行 |
|---|---|---|
| Messages Memory tool | Claude请求文件读写，应用执行；可按需读取跨会话资料 | 没有使用该工具协议或Claude API |
| Managed Agents memory stores | 挂载可读写或只读的持久文档目录，保留版本 | 本地JSON快照与自建版本摘要 |
| Dreams服务 | 读取已有库和历史会话，产出独立的新库，整理重复、冲突与过期内容 | 没有调用Dreams接口 |
| 官方dreaming示例 | 分析会话后，再整体组织；带索引和链接的多文件记忆 | 一次模型请求产出最多三项短笔记变更，没有整体组织阶段 |
| 业务会话读取 | 可以通过文件工具按需读取；示例未来会话挂只读库 | 每个请求自动按词项选少量文字注入，无法继续读证据 |
| 更新时间 | 应用决定何时整理，示例可定时运行 | 每题结束更新，下一题可见；这一点符合后台更新思路 |

官方来源：
- [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- [Managed Agents记忆库](https://platform.claude.com/docs/en/managed-agents/memory)
- [Dreams服务](https://platform.claude.com/docs/en/managed-agents/dreams)
- [后台整理示例](https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow)
- [记忆组件研究](https://www.anthropic.com/research/components-of-agent-memory)
- [Claude Code自动记忆](https://code.claude.com/docs/en/memory)

Claude Code自动记忆又是另一条产品路径，本实验启动的是Codex桥接，不会因为参考了MEMORY.md形式或写了名为dream的函数就启用Claude Code的自动记忆。官方Memory tool也主要提供读写接口，并不自动保证总结正确或成绩提升。研究文章强调验证规则、纠错和选择合适内容，本项目这次没有复现这些效果验证环节。

## 四、优先改哪里，以及如何验证

1. 先修适用性。个人发票不得因“发票”二字就读入企业税号前提；换货、价保、退货的提醒分别匹配当前操作和当前政策。用不含正式题号的开发旁例测检索。
2. 将观察与建议分开。成功回执证明发生了某次办理，不证明整段建议通用；失败轨迹里的猜测先待验证。以当前规则、工具能力和正反例核验后才提升置信，不让模型自行声明“有轨迹支持”就完成验证。
3. 增加整体整理。为经验保存适用与不适用条件、来源证据、冲突和撤回记录；合并重复、修订过期内容。允许需要时读取细节，不能把所有内容硬塞进同样短的注入段落。
4. 补可核查的业务恢复。特别是退款流水，应把真实账本核验转换成模型能查询和说明的证据；条件齐全、授权有效时生成草案，顾客暂缓时不执行。
5. 做局部因果对照后再跑全量。冻结相同对话前缀与账本，只比较原经验、删除可疑经验、修正经验三种条件；记录拟案、确认、终态、步数和误操作。开发结果不混入正式成绩，不通过重新采样覆盖官方零分。

本次保留原始三轮成绩；没有启动新正式轮次，也没有为了改善数字修改已完成实验。两组模拟顾客开场大多不完全相同，另有网络与服务器中断恢复，完整限制见[原复盘](复盘.md)。接入官方原生服务会同时改变运行基础设施和可用模型，届时应另设实验，不能把新增结果直接归因于记忆结构。
